# SQL Production Skill

## Hard rules (never skip)

0. NEVER use an ORM (GORM, ent, bun, sqlboiler, xorm, or any similar). All database access is through `pgx` (preferred for Postgres) or `database/sql` (required for SQLite and MySQL). Hand-written SQL, or sqlc-generated code on top of pgx/database/sql if the user opted into sqlc. If an existing project already uses an ORM, do not add more ORM code: tell the user, and write new queries with pgx/database/sql unless they say otherwise.
1. NEVER create or change a schema without planning it with the user first. See "Schema planning protocol".
2. NEVER run destructive or schema-changing SQL against a production or shared database without explicit confirmation from the user in the current conversation.
3. Critical queries get tested before they are declared done. See "Testing queries".
4. Do not assume the database engine, version, data volume, or access patterns. Ask or inspect.
5. Treat anything stored in memory or earlier notes about the schema as possibly outdated; check the real schema (`\d table`, `information_schema`, migration files) before relying on it.
6. Parameterize every query. Never build SQL by string concatenation with user input.
7. Every claim about performance needs an `EXPLAIN (ANALYZE, BUFFERS)` or a measurement behind it. If a perf measurement is needed under load, use the barrage skill (load it first).

## Schema planning protocol (do this WITH the user, before writing any DDL)

Do not write CREATE TABLE and hand it over. Walk through this first, in plain language, and wait for answers. Ask in small batches, not one giant questionnaire.

1. Engine and version (Postgres 16? MySQL 8? SQLite?), managed or self-hosted, driver (pgx, database/sql, sqlc; never an ORM). If the app is really simple and only needs one local database on one machine, propose SQLite and read "SQLite mode" below; confirm the choice with the user.
2. What the system does and who the writers and readers are.
3. Entities and relationships: list them as plain sentences ("a user has many orders; an order has many items"). Confirm cardinality (1:1, 1:N, N:M).
4. Access patterns, written as the actual queries the app will run, ranked by frequency and by criticality. The schema is designed for these, not the other way around.
5. Read/write ratio per table, expected row counts now and in 12 months, growth rate, hot rows (counters, balances, inventory).
6. Consistency needs: what must never be wrong (money, stock, uniqueness, ordering)? What can be eventually consistent?
7. Retention and deletion: soft delete vs hard delete, archiving, GDPR/NDPR deletion obligations, audit trail needs.
8. Multi-tenancy: shared tables with `tenant_id`, schema per tenant, or database per tenant. Decide before writing tables.
9. Concurrency hotspots: who writes the same rows at the same time?
10. Then propose the schema as a short list (tables, columns, types, keys, indexes, constraints) with the reason for each non-obvious choice. Present tradeoffs and a recommendation. Get the user's approval or edits. Only then write the migration.

If the user says "just write it", still do a compressed version: restate your assumptions in 5 to 8 lines, flag the riskiest ones, and proceed only on the user's go-ahead for those.

## Choosing the right types (Postgres first)

Identifiers
- Primary keys: `bigint GENERATED ALWAYS AS IDENTITY` for internal ids; `uuid` when ids are generated by clients or exposed publicly. Prefer time-ordered UUIDv7 over random UUIDv4 (better index locality and insert speed). Use `int` only when the table is certain to stay small.
- Public ids and internal ids can differ: internal `bigint` PK, external `uuid` or short random id with a unique index.
- Never use natural keys that can change (email, phone) as primary keys.

Numbers
- Money: `numeric(p,s)` (for example `numeric(19,4)`) or integer minor units (kobo/cents) in `bigint` with a separate `currency` column. NEVER `float`/`real`/`double precision` for money.
- Counts and quantities: `integer`/`bigint`; `smallint` only for small bounded enums or flags where the saving matters.
- `numeric` is slow and large; use it only where exactness is needed.
- Avoid `serial` in new code; use identity columns.

Text
- `text` is fine in Postgres; `varchar(n)` only when the length limit is a real business rule. Add `CHECK (length(...) <= n)` when needed.
- `citext` or a lowercase expression index for case-insensitive uniqueness (emails, usernames).
- Use `char(n)` essentially never.
- MySQL: choose `utf8mb4` and a proper collation; watch index key length limits.

Time
- `timestamptz` for instants, always. Store UTC, convert at the edge. Avoid `timestamp without time zone` unless you really mean wall-clock time.
- `date` for dates, `interval` for durations, `time` rarely.
- Never store timestamps as strings or epoch integers unless there is a concrete reason.
- `created_at timestamptz NOT NULL DEFAULT now()`, `updated_at` maintained by trigger or app.

Booleans, enums, flags
- `boolean` for true/false, with `NOT NULL DEFAULT`. Avoid nullable booleans (three states).
- Small fixed sets: a `text` column with a `CHECK (col IN (...))`, or a lookup table with a foreign key (easy to extend). Native `ENUM` types are painful to change (removing/reordering values); use only for truly stable sets.

Structured and semi-structured
- `jsonb` (never `json`) for flexible attributes. Promote fields you filter or join on to real columns with indexes. Do not hide relational data in jsonb.
- Arrays (`int[]`, `text[]`) for small, simple lists you query with `ANY`/`@>`; use a join table when the elements need their own attributes or integrity.
- `inet`/`cidr` for IPs, `uuid` for uuids, `bytea` for binary (store big files in object storage, not the DB), `tsvector` for search, range types (`tstzrange`) for intervals with exclusion constraints, `ltree` for hierarchies when appropriate.

Nullability and defaults
- Default to `NOT NULL`. Use NULL only when "unknown/not applicable" is a real state. Give columns sensible defaults.
- Remember `NULL` semantics: `= NULL` never matches, `NOT IN` with NULLs returns nothing (use `NOT EXISTS`), unique constraints allow multiple NULLs (use `NULLS NOT DISTINCT` in PG15+ if needed).

Column order
- Put wide fixed-size columns first (bigint, timestamptz, uuid), then smaller ones, then variable-length (text, jsonb) last, to reduce alignment padding on large tables.

## Constraints and integrity (let the database enforce truth)

- `PRIMARY KEY` on every table.
- `FOREIGN KEY` with explicit `ON DELETE` behavior (`RESTRICT`/`NO ACTION` by default, `CASCADE` only when children truly cannot outlive the parent, `SET NULL` for optional links). Index every foreign key column.
- `UNIQUE` constraints for business uniqueness (email per tenant, one active subscription per user via partial unique index).
- `CHECK` constraints for invariants (`amount >= 0`, `status IN (...)`, `end_at > start_at`).
- `NOT NULL` everywhere it holds.
- Exclusion constraints (`EXCLUDE USING gist`) for no-overlap rules (bookings).
- Do not rely on app code alone for integrity; apps have bugs and multiple writers.
- Money and stock ledgers: prefer append-only ledger rows (immutable entries) with balances derived or maintained transactionally, not mutated-in-place numbers with no history.
- Naming: `snake_case`, singular or plural table names consistently, `<table>_id` for foreign keys, name constraints and indexes explicitly (`orders_customer_id_idx`) so migrations can reference them.

## Designing for reads vs writes

Decide per table, with the user, whether it is read-heavy, write-heavy, or mixed. Then:

Read-heavy tables
- More indexes are acceptable: composite, covering (`INCLUDE`), partial, expression.
- Denormalize deliberately (store derived columns, counters, snapshots) when joins on hot read paths are the cost; keep them correct with triggers, transactional app code, or periodic rebuild jobs; document the source of truth.
- Materialized views for expensive aggregates (refresh `CONCURRENTLY`, needs a unique index), or rollup/summary tables updated incrementally.
- Read replicas for scale-out reads; know replication lag and route read-your-writes traffic to the primary.
- Caching layer (Redis or in-process) for hot reads, with an invalidation plan.
- Keyset pagination, not `OFFSET`.
- Covering indexes for index-only scans; keep the visibility map fresh with autovacuum.
- Statistics: `ANALYZE`, extended statistics for correlated columns.

Write-heavy tables
- Fewer indexes: every index is paid for on every insert/update/delete. Index only what queries need; drop unused ones (`pg_stat_user_indexes.idx_scan = 0`).
- Keep rows narrow; move rarely-used large columns to a side table.
- `fillfactor` 70 to 90 on update-heavy tables to enable HOT updates; avoid updating indexed columns.
- Batch writes: multi-row `INSERT`, `COPY`, `unnest()` arrays, pgx batch/pipeline. One round trip per batch, not per row.
- Append-only/event tables partitioned by time; drop old partitions instead of mass `DELETE`.
- BRIN indexes for huge append-ordered tables.
- Avoid hot rows (one counter row everyone updates): shard the counter into N rows and sum, or aggregate asynchronously from an event log.
- Avoid triggers doing heavy work on hot write paths.
- `UNLOGGED` tables only for disposable data.
- Tune WAL/checkpoints (`max_wal_size`, `checkpoint_timeout`) for sustained write load; group commit; `synchronous_commit = off` only for data that may lose the last few milliseconds on crash.
- Foreign keys and unique checks cost writes; keep them anyway when integrity matters.

Mixed tables
- Separate the hot write path from the hot read path: write to a narrow table or log, read from a derived/denormalized view or cache.
- CQRS-style split or outbox/CDC to propagate changes to read models.

## Writing queries well

- Select only needed columns. No `SELECT *` in application code.
- Always have a deterministic `ORDER BY` when order matters (add a unique tiebreaker like `id`).
- Always bound result sets (`LIMIT`) unless the full set is genuinely required.
- Use explicit `JOIN ... ON` syntax. Name columns with table aliases to avoid ambiguity.
- `EXISTS`/`NOT EXISTS` instead of `IN (subquery)`/`NOT IN` when NULLs or large subqueries are involved; `COUNT(*) > 0` is wasteful.
- Keep `WHERE` predicates sargable: no functions on the indexed column (`lower(email) = $1` needs an expression index; `created_at >= $1 AND created_at < $2` instead of `date(created_at) = $1`); match parameter types to column types to avoid implicit casts that defeat indexes.
- Avoid leading-wildcard `LIKE '%x'`; use `pg_trgm` or full-text search.
- Use `UNION ALL` unless you need de-duplication.
- CTEs: readable, inlined by default in PG12+; use `MATERIALIZED` only when you want the barrier.
- Window functions for ranking/running totals instead of self-joins.
- Upserts with `INSERT ... ON CONFLICT (...) DO UPDATE`; make the conflict target explicit.
- `RETURNING` to get generated values without a second query.
- Bulk fetch with `WHERE id = ANY($1::bigint[])`, never N+1 loops.
- Avoid `OFFSET` for deep pages; use keyset pagination: `WHERE (created_at, id) < ($1, $2) ORDER BY created_at DESC, id DESC LIMIT $3`.
- Count carefully: exact `COUNT(*)` on big tables is a scan; consider approximate counts, cached counters, or "has more" pagination.
- Use `FILTER (WHERE ...)` aggregates instead of multiple queries.
- Use set-based operations over row-by-row loops (cursor/procedural loops are slow).
- Dates: half-open ranges `[start, end)`, never `BETWEEN` for timestamps.
- Be explicit about time zones; do date bucketing with `date_trunc(... AT TIME ZONE ...)` consciously.
- Format for readability: one clause per line, consistent casing, comments on non-obvious logic.

## Indexing rules

- Index for the access patterns agreed in the schema plan: `WHERE`, `JOIN`, `ORDER BY`, and foreign keys.
- Composite index column order: equality columns first, then range or sort column. The index serves left-prefixes.
- Covering index with `INCLUDE (...)` for hot read queries; partial index (`WHERE deleted_at IS NULL`, `WHERE status = 'pending'`) for hot subsets; expression index for computed lookups.
- Types: B-tree default; GIN for jsonb/arrays/full text; GiST/SP-GiST for geometry/ranges; BRIN for huge naturally ordered tables; hash rarely.
- Unique indexes enforce business rules, not just speed.
- Create in production with `CREATE INDEX CONCURRENTLY` (cannot run inside a transaction block); check for `INVALID` indexes afterward.
- Verify an index is actually used (`EXPLAIN`), and later via `pg_stat_user_indexes`. Drop duplicates and unused ones.
- Do not index low-selectivity columns alone (a boolean) unless partial.
- Small tables may legitimately seq-scan; do not index to "fix" a plan the planner got right.

## Testing queries (required for critical stuff)

"Critical" means: money, balances, inventory, permissions/auth, anything that deletes or updates many rows, anything on a hot path, anything with concurrency risk, migrations on big tables. For these, do all of the following before calling it done. For non-critical queries, at minimum run it once and look at the result.

1. Test against realistic data: volume and distribution similar to production (skewed values, NULLs, duplicates, big tenants). A query that is fine on 100 rows can be a disaster on 10 million. Generate data with `generate_series` or a seed script if needed.
2. Correctness tests: write expected results by hand for small fixtures and compare. Cover empty set, single row, boundary values, NULLs, duplicates, ties in ordering, time zone edges, and negative/zero amounts.
3. Run `EXPLAIN (ANALYZE, BUFFERS)`; confirm the plan (index used, no unexpected seq scan, estimated rows near actual rows, no disk-spilling sort) and record the time.
4. Write queries: test inside a transaction and `ROLLBACK` first; check affected row count equals what you expect; for bulk `UPDATE`/`DELETE` run the equivalent `SELECT count(*)` with the same `WHERE` first and show it to the user.
5. Concurrency tests for read-modify-write logic: run two or more sessions at the same time against the same rows (two psql sessions, or a Go test with N goroutines using separate connections) and assert the invariants (no negative stock, no double spend, no duplicate rows). See concurrency section.
6. Constraint tests: confirm violations actually fail (insert duplicate, bad FK, negative amount) and that error codes are handled by the app (`23505` unique, `23503` FK, `23514` check, `40001` serialization failure, `40P01` deadlock).
7. Migration tests: run up and down on a copy of production-shaped data, measure duration and lock behavior, confirm it is safe online.
8. Automate: put these as repeatable tests in the repo (Go tests with a real Postgres via testcontainers or docker compose, or pgTAP), not one-off manual checks. Use a real database engine in tests, not a mock, for anything involving SQL semantics.
9. Under load: if latency under concurrency matters, load test with the barrage skill (load it first), including the DB runner against the actual queries.
10. Report: show the user the query, the test data shape, the plan summary, the timing, and the cases covered. Say what was NOT tested.

## Transactions

- Use a transaction whenever multiple statements must succeed or fail together. A single statement is already atomic.
- Keep transactions SHORT. No network calls, no user think-time, no slow computations inside an open transaction. Open late, commit early.
- Do reads that do not need atomicity outside the transaction.
- Always handle failure: rollback on error, `defer tx.Rollback()` pattern in Go (safe after commit), and check the commit error.
- Never leave a transaction open on an error path or in a leaked connection. Set `idle_in_transaction_session_timeout`.
- Set `statement_timeout` and `lock_timeout` (per session, per role, or `SET LOCAL` inside the transaction) so nothing waits forever.
- Pass `context` with deadlines to every query; cancel on timeout.
- Retries: wrap transactions in a retry loop for serialization failures (`40001`) and deadlocks (`40P01`), with a small bounded retry count, backoff, and jitter. The whole transaction must be re-executed, and must be safe to re-run (no external side effects inside; send emails/events after commit, or use an outbox).
- Make writes idempotent where retries or duplicates can occur: unique idempotency key column with `ON CONFLICT DO NOTHING`, then read the stored result.
- Outbox pattern: write the business row and an outbox row in the same transaction; a separate worker publishes events. Avoids the "DB committed but message lost" problem (dual write).
- Savepoints (`SAVEPOINT`) for partial rollback inside a transaction; know that heavy savepoint use hurts performance.
- DDL is transactional in Postgres (not in MySQL); use that for safe migrations, except `CREATE INDEX CONCURRENTLY` and a few others.
- Autocommit off/on awareness in drivers; with PgBouncer transaction pooling, session state (`SET`, advisory session locks, prepared statements, `LISTEN`) does not persist across transactions; use `SET LOCAL` and transaction-level locks.

### Isolation levels (Postgres)

- `READ COMMITTED` (default): each statement sees data committed before it started. Allows non-repeatable reads and lost updates in naive read-modify-write. Fine for most things when combined with proper locking or atomic updates.
- `REPEATABLE READ`: snapshot for the whole transaction; detects some concurrent-update conflicts by failing with `40001`; still allows write skew.
- `SERIALIZABLE` (SSI): strongest; prevents anomalies including write skew by aborting transactions with `40001`; requires retry logic; use for complex invariants across rows when explicit locking is awkward.
- Choose the lowest level that preserves the invariants; test the invariant under concurrency.
- MySQL InnoDB defaults to `REPEATABLE READ` with gap locks; behavior differs from Postgres. Check before assuming.

## Locking and concurrency

First choice: avoid needing locks by making the statement atomic.
- Atomic update in one statement: `UPDATE accounts SET balance = balance - $1 WHERE id = $2 AND balance >= $1` and check rows affected. This is safe under READ COMMITTED and needs no explicit lock.
- Counters: `SET n = n + 1`, never read-then-write in app code.
- Uniqueness: rely on unique constraints plus `ON CONFLICT`, not "check then insert".
- Conditional state changes: `UPDATE ... SET status = 'paid' WHERE id = $1 AND status = 'pending'` and check the row count (compare-and-swap on state).

Optimistic concurrency
- `version` integer (or `updated_at`) column: `UPDATE ... SET ..., version = version + 1 WHERE id = $1 AND version = $2`; zero rows affected means conflict; reload and retry or return 409.
- Best when conflicts are rare and holding locks across user think-time is unacceptable.

Pessimistic locking
- `SELECT ... FOR UPDATE` locks the selected rows until the transaction ends; use when you must read, decide in app code, then write.
- Lock modes: `FOR UPDATE` (will modify), `FOR NO KEY UPDATE` (will modify non-key columns; does not block FK checks, usually the better choice), `FOR SHARE`, `FOR KEY SHARE`.
- `NOWAIT` to fail immediately instead of waiting; `SKIP LOCKED` to skip locked rows (job queues, work distribution); `lock_timeout` to bound waits.
- Lock the fewest rows for the shortest time. Select by primary key or an indexed condition, so the lock set is small and predictable.
- Job queue pattern: `SELECT id FROM jobs WHERE status = 'pending' ORDER BY id LIMIT 10 FOR UPDATE SKIP LOCKED`, then mark in the same transaction. Index on the pending subset (partial index).
- Advisory locks (`pg_advisory_xact_lock(key)`) for application-level mutexes (one worker per tenant, singleton jobs). Prefer transaction-scoped over session-scoped (session-scoped leak with connection pools).
- Table locks (`LOCK TABLE`) almost never; they block everything.

Deadlocks
- Cause: two transactions lock the same rows in different orders. Prevention: always lock rows in a consistent global order (sort ids ascending before locking or updating in a batch), keep transactions short, update fewer rows per transaction.
- Handle `40P01` with retry. Log deadlock details (`log_lock_waits = on`, `deadlock_timeout`).
- Foreign keys take implicit locks on parent rows; hot parent rows can serialize child inserts. Use `FOR NO KEY UPDATE` style where appropriate.

Hot rows and contention
- A single hot row (global counter, one account balance everyone touches, inventory of a flash-sale item) serializes writers. Options: shard into N rows and sum; queue updates and apply in batches; reserve-then-confirm patterns; move the counter to Redis and reconcile; use ledger inserts (append-only, no row contention) and compute balance by sum or periodic snapshot.

Race-condition checklist (look for these patterns in any code you review or write)
- Read-then-write without a lock or version check (lost update).
- Check-then-insert without a unique constraint (duplicates).
- Two statements that must be consistent but are in separate transactions.
- Balance/stock decrement without a `>= 0` guard or CHECK constraint.
- Using `SELECT count(*)` to decide something then acting on it.
- Using app-side timestamps/ids for ordering across multiple app instances.
- Relying on `now()` ordering to equal commit ordering (it does not; `now()` is transaction start time).
- Relying on sequence/identity values being gapless or commit-ordered (they are neither).
- Reading from a replica right after a write.

Schema changes and locks
- DDL takes strong locks. `ALTER TABLE` waiting behind a long transaction blocks all later queries on that table (lock queue). Always `SET lock_timeout = '2s'` (or similar) for migrations and retry, never let a migration wait indefinitely.
- Avoid long-running transactions on production; they also block vacuum and cause bloat.

## Production safety and migrations

- Migrations are versioned files in the repo (golang-migrate, goose, atlas, sqitch, Flyway). Never hand-edit production schema.
- Every migration is reviewed, tested on production-shaped data, and has a rollback or forward-fix plan.
- Online-safe patterns (Postgres):
  - Add a nullable column: instant. Adding a column with a constant default is instant in PG11+. Volatile defaults rewrite the table; avoid.
  - Add `NOT NULL` safely: add a `CHECK (col IS NOT NULL) NOT VALID`, then `VALIDATE CONSTRAINT` (weaker lock), then set `NOT NULL` (PG12+ uses the validated check to skip the scan), then drop the check.
  - Add foreign keys with `NOT VALID`, then `VALIDATE CONSTRAINT` separately.
  - Create indexes `CONCURRENTLY`.
  - Backfill in small batches (for example 1,000 to 10,000 rows per transaction, keyed by primary key ranges), with sleeps if needed, never one giant `UPDATE`.
  - Changing a column type often rewrites the table: use expand and contract (add new column, dual write, backfill, switch reads, drop old).
  - Renaming a column or table breaks running app versions: use expand/contract with a deploy in between.
  - Dropping a column: first deploy code that stops using it, then drop.
  - Set `lock_timeout` and `statement_timeout` in migration sessions.
- Deploy order: backward-compatible schema change first, then code, then cleanup. Old and new app versions run side by side during a deploy; the schema must work for both.
- Backups: automated, tested restores (an untested backup is not a backup), point-in-time recovery (WAL archiving), retention policy. Know your RPO and RTO.
- Least privilege: separate roles for app (DML only), migrations (DDL), read-only analytics. No superuser in the app. Row-level security where tenant isolation matters.
- Secrets out of the repo; TLS to the database (`sslmode=verify-full`); restrict network access.
- Connection pooling: size pools to the database, not the app (a pool of roughly 2 to 4 times CPU cores is a typical starting point; hundreds of connections hurt throughput). Use PgBouncer for many app instances. Total of all pools must stay under `max_connections`.
- Set per-role defaults: `statement_timeout`, `idle_in_transaction_session_timeout`, `lock_timeout`.
- Monitoring: `pg_stat_statements`, slow query log (`log_min_duration_statement`), `auto_explain`, replication lag, connection count, locks/blocked queries, dead tuples and bloat, cache hit ratio, disk and WAL growth, long-running transactions, autovacuum activity.
- Maintenance: autovacuum tuned for big hot tables, `ANALYZE` after bulk loads, periodic reindex of bloated indexes (`REINDEX CONCURRENTLY`), transaction ID wraparound monitoring.
- Soft delete (`deleted_at`) complicates uniqueness and queries: use partial unique indexes (`WHERE deleted_at IS NULL`) and a view or consistent filter. Decide with the user whether it is really needed.
- Audit trails: append-only audit/history table or trigger-based logging for sensitive tables.
- PII: minimize what is stored, encrypt sensitive columns where required, mask in non-prod copies, never copy production data to dev unmasked.
- Large deletes/updates: batch them, run off-peak, watch replication lag and WAL volume.
- Time-series/log data: partition by time and drop old partitions.
- Run risky statements first as `SELECT`, then in a transaction, check row counts, then commit.
- Have a runbook: how to find and kill a blocking query (`pg_stat_activity`, `pg_blocking_pids`, `pg_cancel_backend`, `pg_terminate_backend`), how to roll back a deploy, how to restore.

## Tooling modes: goose, sqlc, or manual

Goose (migrations) and sqlc (typed query code) are OPTIONS, never defaults. Do not install, configure, or introduce either unless the user chose it or the project already uses it.

How to pick the mode:
1. Inspect the repo first: `goose` in go.mod or Makefile/CI, a migrations dir with `-- +goose Up` files, `sqlc.yaml` / `sqlc.json`, generated `db.go` / `models.go` / `*.sql.go` files.
2. If found, use that tool and follow its section below. Do not mix in a second migration or codegen system.
3. If not found and the task is not trivial (a real project with ongoing schema changes), ask once: "goose, sqlc, both, or manual?" and remember the answer for the rest of the conversation.
4. If the user says nothing and the task is simple, use manual mode.

Manual mode (default for simple stuff, scripts, prototypes, one-off tables, small services with a handful of queries):
- Write the migration as a plain numbered or timestamped `.sql` file by hand (`0001_create_users.sql`), with the up statements and a commented or separate down section. Tell the user how to apply it with whatever they already use (`psql -f`, their runner).
- Write the queries as plain SQL strings with `$1, $2` parameters and hand-written Go (`database/sql` or `pgx`): `QueryContext`/`QueryRow`/`Exec`, explicit `Scan`, `defer rows.Close()`, check `rows.Err()`, check rows affected for updates/deletes, map `pgconn.PgError` codes (`23505`, `23503`, `23514`, `40001`, `40P01`) to app errors.
- Keep a small repository/store type per aggregate; pass `context.Context` everywhere; accept an interface that both `*sql.DB`/`pgxpool.Pool` and `Tx` satisfy so the same method can run inside or outside a transaction.
- Do the work for the user: write the files and the code, do not just describe it. (Exception: if the user has said they want to write the code themselves to learn, explain and review instead, per their own instructions.)
- Do not add goose, sqlc, or a codegen step for a simple task. Never add an ORM, ever. Mention the option in one line only if the project is clearly growing into needing it.

### Goose (only if the project uses it or the user opted in)

Detect and confirm: `which goose` / `goose -version`, or `go run github.com/pressly/goose/v3/cmd/goose@latest`. Check the existing migrations directory and its naming style (timestamped or sequential) and follow it. Check the installed version's docs/`goose -h` if unsure about a flag; do not guess.

Configuration (env vars keep commands short and keep secrets out of shell history):
- `GOOSE_DRIVER=postgres`
- `GOOSE_DBSTRING="postgres://user:pass@host:5432/db?sslmode=disable"`
- `GOOSE_MIGRATION_DIR=./db/migrations`
- Equivalent flags: `goose -dir ./db/migrations postgres "$DSN" up`
- Never commit real connection strings.

Commands:
- `goose create add_orders_table sql` creates a new timestamped SQL migration file with Up/Down stubs (for example `20170506082420_add_orders_table.sql`). Use `go` instead of `sql` for a Go migration. Add `-s` (`goose -s create ...`) to number new files sequentially (`00001_...`) instead of by timestamp.
- `goose up` applies all pending; `goose up-by-one` applies one; `goose up-to VERSION` applies up to a version.
- `goose down` rolls back the latest; `goose down-to VERSION` rolls back to a version.
- `goose redo` = down then up of the latest (good for testing a new migration).
- `goose reset` rolls back everything (never on production).
- `goose status` shows applied/pending; `goose version` shows the current version.
- `goose validate` checks migration files without running them.
- `goose fix` converts timestamped migration names to sequential numbers. Goose recommends a hybrid approach: timestamped files during development (no version clashes between branches), then run `fix` in CI only when migrations are ready for production so production runs sequential versions.
- `goose down-to 0` rolls back everything (careful); `-allow-missing` applies out-of-order (missing) migrations that would otherwise error; `-table` changes the version table name (use `schema.goose_db_version` if not using the `public` schema); `-timeout` caps query duration; `-v` is verbose; `-no-versioning` applies files in order without tracking (rarely appropriate).
- Other env vars: `GOOSE_TABLE` for the version table name. Goose also loads `.env` files by default; pass `-env=none` to disable, or `-env=<path>` for a specific file. Never commit a `.env` containing real credentials.
- MySQL/MariaDB with the `mysql` driver: the DSN needs `parseTime=true`, and `multiStatements` must be enabled to run several `;`-separated statements in one file.

SQL migration file format:
```sql
-- +goose Up
-- +goose StatementBegin
CREATE TABLE orders (
    id          bigint GENERATED ALWAYS AS IDENTITY PRIMARY KEY,
    customer_id bigint NOT NULL REFERENCES customers (id),
    amount      numeric(19,4) NOT NULL CHECK (amount >= 0),
    created_at  timestamptz NOT NULL DEFAULT now()
);
CREATE INDEX orders_customer_id_idx ON orders (customer_id);
-- +goose StatementEnd

-- +goose Down
-- +goose StatementBegin
DROP TABLE orders;
-- +goose StatementEnd
```
Rules for goose files:
- Each file must contain exactly one `-- +goose Up`. `-- +goose Down` is optional, and if both exist, Up must come first.
- Statements are delimited by semicolons, and every statement must END with a semicolon or goose will not recognize it. Anything with semicolons inside its body (PL/pgSQL functions, triggers, `DO` blocks) must be wrapped in `-- +goose StatementBegin` / `-- +goose StatementEnd`. Wrapping every block is fine and clearer.
- Each migration runs inside a transaction by default. For statements that cannot run in a transaction (`CREATE INDEX CONCURRENTLY`, `CREATE DATABASE`), put `-- +goose NO TRANSACTION` at the top of the file. It applies to BOTH the Up and Down of that file. Keep such a migration to that one concern, because a failure midway cannot be rolled back automatically.
- Environment variable substitution is off by default. `-- +goose ENVSUB ON` / `-- +goose ENVSUB OFF` enable it for the statements between them (`${VAR}`, `${VAR:-default}`, `${VAR-default}`, `${VAR?err_msg}`; `${VAR:?err_msg}` is NOT supported). Avoid it inside PL/pgSQL bodies where `$$` and `$1` must stay literal; wrap the annotations tightly around only the part that needs substitution.
- Set `SET LOCAL lock_timeout = '2s';` (inside transactional migrations) or `SET lock_timeout = '2s';` (in NO TRANSACTION files) at the top of migrations that alter busy tables, so they fail fast instead of queueing behind long transactions; then retry.
- One logical change per migration file. Name it for what it does (`add_orders_status_index`).
- Always write a Down. If a migration is truly irreversible (data drop), say so explicitly in a comment and make Down raise or no-op deliberately, and tell the user.
- NEVER edit a migration that has already been applied anywhere shared (staging, production, a teammate's DB). Write a new migration to fix it. Editing is only acceptable for a file that has never left the author's machine.
- Data backfills: separate migration from the schema change, batched, and keep them out of the transactional schema migration if they are large (use a Go migration or an out-of-band job).
- Follow the online-safe patterns in "Production safety and migrations" above (add nullable, validate constraints separately, create indexes concurrently, expand/contract).
- Test every new migration with `goose up`, `goose down`, `goose up` (or `goose redo`) on a scratch database before handing it over. For big tables, test timing and locks on production-shaped data.
- Version conflicts between branches (two people create migrations with similar timestamps): rebase, check `goose status`, and renumber/fix rather than hand-editing the version table.
- Do not hand-edit the `goose_db_version` table unless the user explicitly asks and understands the risk.

Embedding and running from Go (when the app should migrate itself or in tests):
```go
//go:embed migrations/*.sql
var embedMigrations embed.FS

goose.SetBaseFS(embedMigrations)
if err := goose.SetDialect("postgres"); err != nil { return err }
if err := goose.Up(db, "migrations"); err != nil { return err }  // db is *sql.DB
```
- Embedding is read-only: it works for applying existing migrations. `create` and `fix` still operate on the real filesystem. Pass the directory name inside the embed (`"migrations"`) to `goose.Up`, because embedding keeps the directory structure.
- Goose also has a `goose.NewProvider` API (the repo has `provider*.go` files and a `lock` package); check the version in go.mod and the goose docs before using it, and follow whichever style the project already uses. The embed example above is the older global-function style from the README.
- Go migrations (functions registered with `goose.AddMigration(Up, Down)`, files must start with a number followed by an underscore, and need your own goose binary that imports the migrations package) exist for data backfills that SQL cannot express. Prefer SQL migrations unless logic is genuinely needed.
- Prefer running migrations as a separate deploy step (CI/CD job or init container) over every app instance migrating on startup, to avoid races and long startup locks. If you must migrate on startup, make sure only one instance can do it at a time (a Postgres advisory lock via `pg_advisory_lock`, or goose's locking support if the installed version has it; verify in its docs).
- In tests, run `goose.Up` against a fresh container database per package or per test run.

### sqlc (only if the project uses it or the user opted in)

What it does: you write SQL, sqlc generates type-safe Go code. The SQL is the source of truth. Do not hand-edit generated files.

Detect and confirm: `sqlc version`, a `sqlc.yaml` in the repo. If none exists and the user opted in, create one after confirming the layout with them.

Typical `sqlc.yaml` (version 2) with goose migrations as the schema source:
```yaml
version: "2"
sql:
  - engine: "postgresql"
    schema: "db/migrations"        # sqlc reads the goose "Up" sections and ignores "Down"
    queries: "db/queries"
    gen:
      go:
        package: "db"
        out: "internal/db"
        sql_package: "pgx/v5"      # or "database/sql"
        emit_json_tags: true
        emit_empty_slices: true
        emit_interface: false
        overrides:
          - db_type: "uuid"
            go_type:
              import: "github.com/google/uuid"
              type: "UUID"
          - db_type: "uuid"
            nullable: true
            go_type:
              import: "github.com/google/uuid"
              type: "UUID"
              pointer: true
          - db_type: "pg_catalog.timestamptz"
            go_type: "time.Time"
          - db_type: "pg_catalog.numeric"
            go_type:
              import: "github.com/shopspring/decimal"
              type: "Decimal"
```
Override rules (checked against the sqlc docs):
- For Postgres, `db_type` must use `pg_catalog.`-prefixed names where they exist (`pg_catalog.timestamptz`, `pg_catalog.numeric`, `pg_catalog.int8`); `uuid` has no prefix. The supported list lives in sqlc's `postgresql_type.go`.
- A `db_type` override applies to EITHER nullable OR non-nullable columns, never both. For both, write two entries, one with `nullable: true`.
- `go_type` is either a fully qualified string (`"time.Time"`) or a map with `import`, `package`, `type`, `pointer`, `slice`.
- `column: "table.column"` overrides a single column and takes precedence over `db_type`.
- `sql_package` is one of `pgx/v4`, `pgx/v5`, `database/sql` (default `database/sql`). With pgx/v5 the default uuid and timestamp types come from pgtype, which is why overrides are often wanted.
- `:copyfrom` additionally requires `sql_driver: "github.com/jackc/pgx/v5"` in the `gen.go` block.
- `emit_methods_with_db_argument: true` makes generated methods take the DB/tx as an argument instead of storing it on `Queries`.
- Match the project's existing config if one exists; check the docs for the installed version (`sqlc version`) before using any option not shown here.

Query files (`db/queries/orders.sql`) use annotations:
```sql
-- name: GetOrder :one
SELECT id, customer_id, amount, created_at
FROM orders
WHERE id = $1;

-- name: ListOrdersByCustomer :many
SELECT id, customer_id, amount, created_at
FROM orders
WHERE customer_id = sqlc.arg(customer_id)
  AND (created_at, id) < (sqlc.arg(cursor_created_at)::timestamptz, sqlc.arg(cursor_id)::bigint)
ORDER BY created_at DESC, id DESC
LIMIT sqlc.arg(page_size);

-- name: CreateOrder :one
INSERT INTO orders (customer_id, amount)
VALUES ($1, $2)
RETURNING id, customer_id, amount, created_at;

-- name: MarkOrderPaid :execrows
UPDATE orders SET status = 'paid'
WHERE id = $1 AND status = 'pending';
```
Annotation meanings:
- `:one` returns a single row (errors with `sql.ErrNoRows`/`pgx.ErrNoRows` if none)
- `:many` returns a slice
- `:exec` returns only an error
- `:execrows` returns rows affected (use for compare-and-swap updates and to detect "nothing happened")
- `:execresult` returns the driver result
- `:execlastid` returns the generated id from the driver result (MySQL-style; on Postgres use `RETURNING` with `:one` instead)
- `:batchexec`, `:batchone`, `:batchmany` for batch mode. These work ONLY with Postgres and the pgx drivers (`pgx/v4`, `pgx/v5`), generating Go code. They take a slice of params and return a batch object with `Exec` / `QueryRow` / `Query` (each takes a callback) and `Close`.
- `:copyfrom` for fast bulk inserts. It is driver specific and needs `sql_driver` set in the config (see override rules above).
- Macros: `sqlc.arg(name)` gives a named parameter; `sqlc.narg(name)` is the same but always nullable (for optional filters: `WHERE (sqlc.narg(status)::text IS NULL OR status = sqlc.narg(status))`); `sqlc.embed(table)` embeds a whole model struct in join results.
- `sqlc.slice("ids")` exists for drivers that cannot pass slices to `IN` (MySQL, SQLite). It is not for Postgres and cannot be used with prepared statements. On Postgres use `= ANY(sqlc.arg(ids)::bigint[])`.
- Named parameters: `sqlc.arg(name)`, `sqlc.narg(name)`, and the `@name` shortcut for `sqlc.arg` (not supported on MySQL; there is no nullable shortcut). The docs do not say whether positional and named parameters can be mixed in one query, so do not mix them: use one style per query (named is clearer past two parameters) and run `sqlc compile` to confirm.

Workflow whenever the schema or a query changes:
1. Write/modify the migration (goose or manual) first.
2. Write/modify the query in `db/queries/*.sql`.
3. Run `sqlc compile` (static check of syntax and types), then `sqlc generate`. Run `sqlc vet` if lint rules are configured. Other subcommands that exist: `sqlc diff` (compare generated files to what is on disk), `sqlc fmt`, `sqlc analyze`, `sqlc parse`, `sqlc init`, `sqlc version`, plus `-f` to pick an alternate config file.
4. Commit the generated code together with the SQL changes. In CI, run `sqlc diff` (or `sqlc generate` followed by `git diff --exit-code`) to catch forgotten regeneration.
5. Use the generated `Queries` type in app code; build transactions with the generated `WithTx`:
```go
tx, err := pool.Begin(ctx)
if err != nil { return err }
defer tx.Rollback(ctx)
q := queries.WithTx(tx)
// q.CreateOrder(...), q.DecrementStock(...)
if err := tx.Commit(ctx); err != nil { return err }
```

sqlc rules:
- Never edit generated files; change the SQL or config and regenerate.
- Keep queries explicit: list columns instead of `SELECT *`, so adding a column does not silently change generated structs and call sites.
- One query per business operation; name them for intent (`ReserveStock`, not `UpdateProduct2`).
- Put locking and atomic-update logic in the SQL itself (`... WHERE balance >= $1`, `FOR UPDATE SKIP LOCKED`, `ON CONFLICT`), and handle retries and isolation in the Go transaction wrapper.
- sqlc is poor at truly dynamic queries (variable filters, dynamic ORDER BY, variable column sets). Options: optional filters via `sqlc.narg` with `IS NULL OR` (watch the plan; it can defeat indexes, test with `EXPLAIN`), several fixed queries for the few real variants, or write that one query by hand with pgx next to the generated code. Do not contort the SQL to fit.
- Type overrides must be consistent across the project (uuid, numeric, timestamptz, jsonb) so domain code is not littered with conversions.
- Test queries against a real Postgres (as in "Testing queries"); sqlc proving the SQL compiles does not prove it is correct, fast, or concurrency-safe.
- sqlc plus goose together: goose owns schema changes, sqlc reads the same migrations directory as its schema, so there is a single source of truth. After every new migration, run `sqlc generate`. sqlc ignores the Down sections of goose files when parsing.
- Ordering trap: sqlc parses migration files in lexicographic order, not numeric. Sequential goose names must be zero-padded (`001_`, `002_`, ... `010_`), because `10_x.sql` sorts before `9_y.sql` and sqlc would then see the schema changes in the wrong order. Default timestamp names (`20240101120000_x.sql`) are fine. Check this whenever sqlc output looks wrong after a rename or `goose fix`.
- sqlc does not run migrations; it only reads them. It understands CREATE TABLE and ALTER TABLE; a construct it cannot parse is the usual cause of a generate failure.
- If sqlc cannot parse a migration construct (some DO blocks, exotic extensions), keep a separate `schema.sql` snapshot for sqlc or exclude that file, and tell the user.

### Mixing modes

- Goose + sqlc: standard pairing, described above.
- Goose + manual queries: migrations through goose, hand-written Go for queries.
- sqlc + manual migrations: point sqlc `schema` at the hand-written migration files or a maintained `schema.sql`.
- For one-off simple queries in an sqlc project, still add them to the `.sql` query files rather than writing a stray hand-written query, unless it is the dynamic-query exception above.
- In a manual-mode project, do the simple stuff by hand and do not propose tooling unless the user asks.

## SQLite mode (really simple apps that need one local database)

Use SQLite when the app is genuinely simple: one machine, one local database file, a CLI tool, a small single-binary service, a desktop/embedded app, a prototype, or a test database. Propose it to the user at the start of schema planning when the app fits, and confirm; do not assume it.

Do NOT use SQLite when:
- more than one host needs the same database (the file cannot be shared across machines; WAL does not work over a network filesystem because processes share memory through the wal-index)
- many processes or goroutines need heavy concurrent writes (SQLite allows only one writer at a time)
- the app needs row-level locking, replicas, or Postgres-only features (jsonb/GIN, partitioning, `FOR UPDATE SKIP LOCKED`)
In those cases use Postgres, and tell the user why.

Everything in the hard rules still applies: no ORM, schema planned with the user first, critical queries tested, parameterized queries, migrations as files in the repo. The Postgres-specific sections above (types, locking, `FOR UPDATE`, `CONCURRENTLY`, `pg_stat_*`) do NOT carry over; use this section instead.

### Driver and access

- Default driver: `modernc.org/sqlite`, a CGo-free port of SQLite (no C toolchain needed, easy cross-compiling). Import it for side effects and open it with the driver name `sqlite`: `sql.Open("sqlite", dsn)`. If the user prefers the CGo driver (`mattn/go-sqlite3`, driver name `sqlite3`), follow their choice and check its docs, since DSN options differ.
- Use `database/sql` (pgx is Postgres-only). Hand-written SQL, no ORM.
- Placeholders: use `?` in SQLite queries. Do not paste Postgres `$1` queries across without testing them.
- DSN is a file name or a `file:` URI. Per-connection settings go in the DSN as `_pragma=name(value)` parameters, which the driver runs as `PRAGMA name(value)` on each new connection:
  `file:app.db?_pragma=foreign_keys(1)&_pragma=busy_timeout(5000)&_pragma=synchronous(NORMAL)`
- Why the DSN: PRAGMA state lives on the connection, and `database/sql` pools connections; the driver does not reset state between borrowers. Setting a PRAGMA once with `db.Exec` only affects one pooled connection. Use the DSN (or a connection hook) for anything that must hold on every connection.
- Check the driver's own docs for the exact parameter list before using an option not shown here.

### Required settings (always set these, explicitly)

- `foreign_keys`: OFF by default, per connection, and cannot be changed inside a transaction. Turn it ON in the DSN for every connection, or foreign keys silently do nothing.
- `journal_mode=WAL`: lets readers and a writer work at the same time (readers do not block the writer and vice versa). WAL is persistent in the database file, so setting it once at startup with `db.Exec("PRAGMA journal_mode=WAL")` is enough, and the result should be checked: it returns `wal` on success and the old mode if it could not switch.
- `busy_timeout`: how long a connection waits for a lock before returning `SQLITE_BUSY`. Set a few seconds (for example 5000 ms). The SQLite page is ambiguous about its scope, so also test that it behaves as expected with your driver.
- `synchronous`: with WAL, `NORMAL` keeps the database consistent and survives application crashes, but the last commits can be lost after a power loss or OS crash. `FULL` makes WAL commits durable at some cost in speed. Default to `NORMAL` for ordinary apps; use `FULL` when losing the last few commits is unacceptable (money, orders), and tell the user which was chosen and why.
- Run `PRAGMA optimize;` just before closing the database (short-lived connections), or on open with `PRAGMA optimize=0x10002;` and periodically for long-lived ones. Also run it after schema changes, especially after `CREATE INDEX`.

### Connection pool and the single-writer rule

- SQLite has one writer at a time. Concurrent writers queue behind the lock and fail with `SQLITE_BUSY` once `busy_timeout` runs out.
- Bound the pool: `database/sql` opens connections without limit by default, so always call `db.SetMaxOpenConns(n)`.
- Simplest safe setup for a small app: `SetMaxOpenConns(1)`. Writes cannot collide; reads are serialized too, which is fine at small scale. Pitfall: with one connection, never hold an open `rows` while running another query on the same `db`, or the app deadlocks waiting for its own connection. Always `rows.Close()` first and always check `rows.Err()`.
- If read throughput matters: two handles to the same file, a write handle with `SetMaxOpenConns(1)` and a read handle with a few connections (read-only access), both in WAL mode.
- For read-then-write transactions, start them as write transactions up front (SQLite's `BEGIN IMMEDIATE`) instead of reading first and upgrading, because an upgrade can fail immediately with `SQLITE_BUSY` instead of waiting. Check the driver docs for how to set the transaction lock mode (some drivers use a `_txlock` DSN option).
- Handle `SQLITE_BUSY` with a bounded retry (backoff plus jitter), and keep write transactions short, exactly as in the Transactions section.
- No `SELECT ... FOR UPDATE` or row locks exist. Use atomic single-statement updates (`UPDATE ... SET balance = balance - ? WHERE id = ? AND balance >= ?` and check rows affected), unique constraints with `ON CONFLICT`, and short write transactions.

### Types and schema (SQLite is different)

- Use `STRICT` tables (SQLite 3.37.0 or newer): `CREATE TABLE t (...) STRICT;`. Without it, SQLite stores whatever value you give a column, even the wrong type (text `'xyz'` into an `INTEGER` column), because types are only hints (affinity).
- STRICT allows only these column types: `INT`, `INTEGER`, `REAL`, `TEXT`, `BLOB`, `ANY`. Anything else is rejected. `INTEGER PRIMARY KEY` is the rowid alias (an `INT PRIMARY KEY` is not). A value that cannot be losslessly converted raises a datatype constraint error. `PRAGMA integrity_check` and `quick_check` also verify types in STRICT tables.
- Databases that use STRICT tables need SQLite 3.37.0 or later to read and write them. Note this if the file will be opened by other tools.
- Mapping of Postgres habits to SQLite (the choices are the user's, propose and confirm):
  - id: `INTEGER PRIMARY KEY` (rowid alias, auto-assigned), or `TEXT`/`BLOB` for uuid (propose time-ordered ids)
  - money: `INTEGER` minor units (kobo/cents) plus a currency column; never `REAL`
  - boolean: `INTEGER` with `CHECK (col IN (0, 1))` and `NOT NULL`
  - timestamps: no native timestamp type. Pick one convention and use it everywhere: `TEXT` ISO-8601 in UTC (`2026-10-10T06:36:00Z`, sorts correctly) or `INTEGER` unix seconds. Never mix.
  - json: `TEXT` (validate with a `CHECK` if desired); no jsonb or GIN
  - small fixed sets: `TEXT` with `CHECK (col IN (...))`
- Keep `NOT NULL`, `CHECK`, `UNIQUE`, `FOREIGN KEY` constraints exactly as in the Constraints section; they work in SQLite (foreign keys only with the PRAGMA on).
- Index for the agreed access patterns as usual (composite, partial, expression indexes exist in SQLite). Verify with `EXPLAIN QUERY PLAN`, not `EXPLAIN ANALYZE`.
- Altering tables is limited; plan the schema carefully up front. Check the SQLite docs before writing a migration that changes or drops columns.

### WAL files, backups, and checkpoints

- In WAL mode the database is the `.db` file plus `-wal` and `-shm` files in the same directory. The WAL file is part of the persistent state: if the database is copied or moved without it, committed transactions can be lost or the database corrupted. Never copy or delete just the `.db` file of a live database, and never delete a leftover `-wal` by hand.
- For backups use SQLite's own backup mechanisms (the online backup API, the `sqlite3` shell's `.backup`, or `VACUUM INTO 'file'`; check which the installed SQLite version supports) rather than a plain file copy of a running database. Test a restore.
- Automatic checkpointing runs when the WAL reaches about 1000 pages (around 4 MB) and when the last connection closes. A long-running read transaction can stall checkpoints and let the WAL grow, so keep read transactions short and close `rows`.
- `page_size` cannot be changed after the database enters WAL mode.
- WAL requires all processes to be on the same host. Never put the database on NFS/SMB or a synced folder.

### Migrations and tooling with SQLite

- Manual mode works as described above: plain numbered `.sql` files applied at startup or by a tiny runner. Fine for the simplest apps.
- Goose supports SQLite (its README examples use the `sqlite3` dialect: `goose sqlite3 ./foo.db status`). With embedded migrations, set the dialect with `goose.SetDialect("sqlite3")` and pass your own `*sql.DB`. For a single-binary app, running embedded migrations on startup is acceptable because only one process owns the file.
- sqlc supports SQLite: set `engine: "sqlite"` and `sql_package: "database/sql"` (pgx is Postgres-only; so are the `:batch*` and pgx `:copyfrom` features). `sqlc.slice("ids")` is the macro for `IN` lists on SQLite. Nullable columns can be emitted as pointers with `emit_pointers_for_null_types` (supported for SQLite). SQLite uses `?` placeholders, so write named parameters with `sqlc.arg(name)` and let sqlc expand them.
- The same tooling-mode rules apply: use goose or sqlc only if the project already has them or the user opted in; otherwise write migrations and queries by hand.

### Testing with SQLite

- Test against real SQLite, never a mock. It is cheap: open a database in `t.TempDir()` for each test or package, apply the migrations, run the checks.
- Prefer a temp file over `:memory:` with a pooled `database/sql`: each pooled connection can get its own separate in-memory database, which produces confusing "no such table" failures.
- Run the same critical-query tests as in "Testing queries": correctness fixtures, constraint violations (confirm foreign keys really fail, which proves the PRAGMA is on), and a concurrency test with several goroutines writing at once to confirm `SQLITE_BUSY` handling and invariants.
- For load, the barrage skill's DB runner supports a pure-Go SQLite driver; load it first if write contention under load matters.

### Graduating to Postgres

Tell the user it is time to move off SQLite when: a second host needs the data, writes from many processes keep hitting `SQLITE_BUSY`, they need replicas, row locks, or Postgres types and extensions, or the data outgrows one machine. To keep the move cheap: keep SQL plain and standard, keep the timestamp and money conventions consistent, avoid SQLite-only tricks, and keep all database access behind a small store layer.

## Common anti-patterns to flag

- Float for money.
- Random UUIDv4 primary keys on huge insert-heavy tables with no reason.
- `timestamp` without time zone for instants.
- Missing index on a foreign key.
- `SELECT *` in app code; unbounded queries; `OFFSET` on deep pages.
- N+1 queries; per-row inserts in a loop.
- Read-modify-write in app code with no lock or version check.
- Check-then-insert instead of a unique constraint.
- Long transactions; transactions open across HTTP/API calls.
- Dual writes (DB plus queue/cache) with no outbox or reconciliation.
- jsonb used as a dumping ground for relational data.
- EAV (entity-attribute-value) tables for data that has a known shape.
- Business rules only in app code with no constraints.
- Unbounded retries; retries without idempotency.
- Giant migrations that rewrite or lock big tables during peak hours.
- Hundreds of DB connections from app pools.
- Mocked database in tests for SQL-heavy logic.
- Relying on implicit row ordering without `ORDER BY`.
- Using `NOT IN` with a nullable subquery.
- Editing production schema by hand.

## How to respond when asked to write SQL

1. Restate the goal and the assumptions (engine, table shapes, data size, concurrency) in a few lines. Ask only the questions that change the answer.
2. If it involves schema design: stop and run the planning protocol with the user before writing DDL.
3. Write the SQL with parameters (`$1`, `$2`), explicit columns, bounded results, and constraints.
4. For critical paths: provide or run the tests from "Testing queries", including concurrency checks, and report results.
5. State the indexes the query needs and why, and the expected plan.
6. State the transaction boundary, isolation level, locking approach, and retry behavior where writes are involved.
7. Flag risks, assumptions, and anything untested.
8. For performance work under load, load the barrage skill first and measure before and after.
